# Repository analysis — 29 October 2026

Full-repo review of `rushi-builds/Quotation-Studio` at `6e8b6f1` (branch
`arena/1a774e12-quotation-studio`). Every claim below was measured in this
checkout: dependencies installed, the QA suite executed, the app booted, and the
API probed. Where something could not be verified (no Chromium, shallow clone)
it is stated instead of guessed.

---

## 1. Executive summary

This is an unusually disciplined codebase for a no-build static app. The
financial engine is pure and heavily tested, the product stance ("never invent a
number") is enforced in code and not just in prose, SQL is fully parameterised,
tokens are hashed, CSRF is enforced, and the app boots and serves correctly.

The problems are not in the *quality* of the work — they are in the
**infrastructure around it**:

| # | Finding | Severity |
|---|---------|----------|
| 1 | The primary test command (`npm test`) is **red** — 4 of 24 suites fail, including two that fail 100% (0/8 and 0/19) | High |
| 2 | **24 of 139 test files (17%)** are not in any npm script; 7 of 8 sampled are broken | High |
| 3 | **80 of 121 test files need a real browser**, none can run here, and there is **no CI** — so most of the suite has no automatic run | High |
| 4 | The two backends are **hand-maintained duplicates** (7,563 lines) and have already drifted (`CODE_VERSION` mismatch) | High |
| 5 | The sign-in page ships **391 KB gzipped** — one 448 KB base64 image inlined in HTML | Medium |
| 6 | The public repo commits real owner/admin emails, the D1 database id and a Drive file id in `wrangler*.toml` | Medium |
| 7 | Migrations have **colliding numbers** and no tracking table; `schema.sql` is not authoritative | Medium |
| 8 | Assistant knowledge is generated by **regex-slicing `finance.js` source** — silent-break risk | Medium |
| 9 | ~10.7 MB of orphaned images; 2.6 MB of legacy duplicate UIs (`review/`, `concept-preview/`) | Low |
| 10 | 68 docs, 30 of them orphaned (nothing links to them) | Low |

The fastest high-value fix is not more features. It is **restoring the test
signal and adding CI**, because everything else on this list is invisible
precisely because nothing runs automatically.

## 2. What the repository actually is

Three products in one repo:

1. **`quotation.html` — the proposal builder.** A single-page app with no build
   step: form on the left, live A4 preview on the right, 15–21 page proposal,
   PDF export via html2canvas → jsPDF. All libraries and fonts are vendored
   locally.
2. **The platform.** Two interchangeable backends behind one `/api` contract:
   - `platform/cloudflare/src/worker.js` — Cloudflare Worker + D1 (production,
     deployed as `qs-studio-rushi`).
   - `platform/local-server/server.js` — Node HTTP server + JSON file store
     (local development).
3. **The staff dashboard** — proposals, versions, publishing, portal links,
   team roles, tasks, reports, billing-free "honesty" states.

`vercel.json` serves the static front end and rewrites `/api/*` to the Worker,
so the same origin serves pages and API.

## 4. Architecture findings

### 4.1 Two hand-maintained backends (highest structural risk)

`worker.js` (3,920 lines) and `server.js` (3,643 lines) are independent copies of
the same API. 180 long lines are byte-identical between them. `server.js`
carries the comment *"These mirror platform/cloudflare/src/worker.js EXACTLY…
a change here is a change there."*

Route groups match exactly (15 `proposals`, 12 `auth`, 4 `team`, 4 `tasks`,
4 `gallery`, 3 `portal`, 3 `notifications`, …) with the local server adding 3
`dev` routes and the Worker adding `catalogue` / `site`.

A comment is not an enforcement mechanism, and §3.2 shows it has already failed
once. This is the change most likely to cost real debugging time later:
every auth, role, recovery, and pricing fix has to be made twice and verified
twice.

**Recommendation:** extract the route layer into one shared module with a small
storage adapter (`D1` vs `JSON file`). Even a mechanical extraction of the
handlers into `platform/shared/` would delete ~3,000 duplicated lines and make
the parity tests structural instead of aspirational.

### 4.2 Assistant knowledge is generated by regex-slicing source code

`scripts/build-assistant-knowledge.cjs` builds the AI assistant's knowledge base
by **matching JavaScript source with regular expressions** and executing it in a
`vm` sandbox:

```js
const presets = vm.runInNewContext('(' + app.match(/const PRESETS = (\{[\s\S]*?\n    \});/)[1] + ')');
...
methods: { subsidy: financeSource.match(/function calcSubsidy\(kwp\) \{[\s\S]*?\n  \}/)[0], ... }
```

This breaks silently on any reformat — a renamed constant, a changed indent, a
moved closing brace. When it breaks, the assistant either fails to build or
serves stale numbers to staff, and the only guard is a test
(`assistant-knowledge.test.mjs`) that is itself in the fragile
`test:assistant` script.

The 12,126-line generated `studio-knowledge.mjs` (337 KB) is also **committed to
git**, so a stale copy is always one forgotten build away.

**Recommendation:** have `finance.js` and `state.js` export the values they
already own (`calcSubsidy`, `DEFAULTS`, `PRESETS`) and import them directly. The
generator then needs no `vm`, no regex, and cannot silently drift.

### 4.3 Database migrations

- **Colliding numbers.** `005`, `006`, `007` each span two unrelated feature
  tracks: `006-catalogue.sql` and `006-profile-info.sql`; `007-site-geo.sql` and
  `007-member-links-likes.sql`. There is also a `005`, `006`, `007`, `008`, `009`
  `*-verify.sql` companion for each. Nothing documents the true order.
- **No tracking.** There is no `schema_migrations` table anywhere in the repo.
  Applied state lives only in someone's memory of which `wrangler d1 execute`
  commands were run.
- **`schema.sql` is not authoritative.** It defines 23 tables, but
  `oauth_rate_limits`, `oauth_attempts` and `oauth_identities` exist only in
  `migrations/003-oauth.sql`. They are self-healed at runtime by
  `platform/oauth-store.mjs` `ensure()`, so this is currently benign — but the
  documented "apply `schema.sql`" path does not produce the schema the code
  expects.
- **`001-drop-all.sql`** sits in the migrations directory and drops every table.
  It is clearly labelled *"NEVER run on a live database"*, which is exactly the
  kind of file that gets run on a live database when it is one `ls` away from
  its siblings.

**Recommendation:** add `platform/migrations/README.md` with the real order, add
a `schema_migrations` table, rename the collisions to `005a/005b`, and move
`001-drop-all.sql` out of `migrations/` into `scripts/` with a confirmation flag.

### 4.4 Front-end delivery

- `quotation.html` loads **37 `<script>` tags and 12 stylesheets**, unbundled.
  This is a deliberate no-build choice and it *works* — the page is only
  23.5 KB gzipped because the payload sits in cacheable external files.
- Cache-busting is **hand-written** `?v=` strings (`?v=appearance-sync11`,
  `?v=review-live-items1`…). A forgotten bump serves stale JS to a returning
  user with no error anywhere. This is the single most likely cause of
  "it works for me but not for them" bug reports.
- **The sign-in page is the exception and it is the worst offender:**

| Page | Raw | Gzipped | Note |
|------|-----|---------|------|
| `index.html` (sign-in) | 536.7 KB | **391.4 KB** | 448 KB is one base64 image inlined in HTML |
| `gallery.html` | 583.3 KB | **431.7 KB** | 563 KB single base64 image |
| `quotation.html` | 113.1 KB | 23.5 KB | correctly externalised |

The first thing every user downloads — the login screen — is 391 KB gzipped and
cannot be cached independently of the HTML. `assets/images/login-bg.jpg` (335 KB)
exists as a file but is not referenced, because its content was inlined instead.

**Recommendation:** move the base64 blobs back to `assets/images/*.webp`, serve
them as `<img src>` / CSS `url()`, and let the browser cache them. This is a
one-file change with a ~370 KB saving on first paint.

## 5. Security review

This is a genuinely careful implementation. Verified strengths:

- **Password hashing**: scrypt with `N = 2^15, r = 8, p = 1` and
  `maxmem = 64 MB`, salted per user, format-versioned (`scrypt$salt$hash`) with a
  legacy fallback — in *both* backends, identically.
- **SQL injection**: **zero** string-interpolated queries in `worker.js`. Every
  statement is positional-bound.
- **CSRF**: enforced, not decorative. `crossSiteBlocked()` rejects state-changing
  requests with a foreign `Origin`/`Referer` (`worker.js:1756`,
  `server.js:1701`). Confirmed live: cross-origin login POST → **403**.
- **Session cookies**: `HttpOnly`, `SameSite=None` only on HTTPS with `Secure`,
  `Lax` on plain HTTP, correctly rationale-commented.
- **Portal tokens**: 32 random bytes, **SHA-256 hash stored**, never the token
  itself; expiry and revocation checked on every read.
- **Secrets**: no `.env`, no private keys, no credentials committed. Sweep clean.
- **XSS**: `esc()` applied consistently in `render.js` (0 unescaped
  `+ form.x` patterns), no `eval` / `new Function` in shipped app code.
- **Zero** `console.log` and **zero** `TODO`/`FIXME` in shipped `assets/js` or
  `platform/`.

### Issues to address

1. **The repository is public** (`isPrivate: false`) and
   `platform/cloudflare/wrangler.toml` + `wrangler.git.toml` commit real
   addresses and ids:
   ```toml
   ADMIN_EMAIL  = "rushidhumal.04@gmail.com"
   OWNER_EMAIL  = "ktmenergyexperts@gmail.com"
   database_id  = "f3c2c763-e497-4617-8392-25605fceeafe"
   GOOGLE_DRIVE_PRODUCT_CATALOG_FILE_ID = "1BaCB5Lwslopl1P4sHahtkw-8Fltk3pyc"
   ```
   The emails are the **bootstrap owner and hidden admin identities** — and the
   code treats their distinctness as a security property ("if they ever match,
   `/api/health` reports the P1 collision"). Publishing them hands an attacker
   the two account names worth targeting, which turns a password brute-force
   into a *targeted* one. The D1 id and Drive file id are lower risk but are
   still identifiers that belong in `[vars]` via `wrangler secret`/environment,
   not in a public git history.

2. **scrypt cost vs. Workers Free.** `N = 2^15` allocates 32 MB and takes tens
   of milliseconds of CPU. Workers Free caps CPU at 10 ms per request. Sign-in
   therefore requires a **Workers Paid** plan. This is worth one line in
   `docs/cloudflare-deploy.md` so nobody debugs a mysterious CPU-exceeded error
   on a downgraded account.

3. **No CSP, no `X-Frame-Options`.** Both are deliberate — the app is designed to
   run inside preview iframes, and CSRF compensates for `SameSite=None`. The
   reasoning is documented in `docs/security-audit-2026-10-04.md`, which
   correctly proposes reporting-only CSP first. Still outstanding, and still the
   largest remaining defence-in-depth gap.

4. **CORS reflects `Origin` with `Access-Control-Allow-Credentials: true`** for
   any host matching the app host. Correct as written, but it means the CSRF
   Origin check is the *only* barrier on those routes — worth an explicit test
   that it covers every mutating route, not just the ones audited.

It is easy to lose this in a findings list, so stating it plainly:

- **The financial model is honest and testable.** `finance.js` is pure (no DOM),
  UMD, and 82 tests assert its behaviour. Subsidy slabs match PM Surya Ghar

# Remediation log — applied in this session

## Fixed

**1. `CODE_VERSION` divergence (real production defect, §3.2 ①)**

`platform/local-server/server.js` reported `reconcile-r1` while
`platform/cloudflare/src/worker.js` reported `proposal-feedback-r1`, even though
the local server's own comment promised the two were identical. Both now
declare `proposal-feedback-r1` (both backends carry the feedback route, so both
are on that feature set). Verified at runtime:

```
GET /api/health -> {"codeVersion":"proposal-feedback-r1","ok":true,"phase":"E"}
```

`qa/roles-parity.test.js` (which enforces cross-backend equality) now passes
that assertion, and `qa/roles-access.test.js` went from asserting a hardcoded
literal to asserting the value the server **source** declares — so a release
bump no longer has to be repeated in three files that can silently disagree.

**2. Two permanently-red suites quarantined (§3.2 ③④)**

`module-autofill.test.js` (0/8) and `product-match.test.js` (0/19) assert a
surface that does not exist anywhere in the app:

- `EquipmentStore.modelEntriesForMake` / `EquipmentStore.findModule` — exported by nothing.
- `inverterWorkbookModel` / `workbookCableProduct` — ids absent from `quotation.html` and `assets/`.

Both were moved out of `npm test` into `npm run test:quarantine`, annotated with
a `QUARANTINED` header explaining exactly what is missing and what a rewrite
needs. Nothing was deleted. The harness bug that caused a *secondary* crash
(missing `proposal-marks.js`, which made `renderTerms` throw through
`root.ProposalMarks`) was fixed in both files regardless.

**3. Excel catalogue suite could not resolve its own dependency (§3.2 ②)**

`excel-module-catalog.test.mjs` imports from `platform/cloudflare/src/`, and
Node resolves bare imports **relative to the importing file** — so `@e965/xlsx`
must be installed under `platform/cloudflare`, not `qa`. Adding it to `qa`
(attempted, then reverted) does not work. The suite now runs 5 pass / 0 fail /
1 skip once `platform/cloudflare` deps are installed, and the CI workflow does
that install explicitly.

The single skipped subtest drove the same removed workbook-picker ids; it is
marked `test.skip` with a reason rather than deleted.

**4. CI added — `.github/workflows/qa.yml`**

The repository had no workflow of any kind. Two jobs:

- **offline** (required): `fetch-depth: 0`, Node 22, both dependency trees,
  `npm test`. Full history is mandatory because the frozen-family check pins
  blob hashes to golden tree `8cc7db1`; a shallow clone reports every frozen
  file as "absent in comparison tree".
- **browser** (opt-in, `continue-on-error`): installs Playwright Chromium,
  starts `platform/local-server/server.js`, runs `npm run test:browser` with
  `QA_BASE`. It has **never been executed on a runner** — flip
  `continue-on-error` to `false` only after it is observed green.
