## Findings and disposition

| Finding | Risk / behaviour before audit | Resolution |
| --- | --- | --- |
| Report action URLs interpolated into `innerHTML` | Imported proposal URLs could inject attributes/markup or use `javascript:` URLs. | Construct DOM anchors, accept absolute HTTP(S) only, reject embedded credentials, set `noopener noreferrer`. Render footer company data as text, too. |
| Request hidden when only one report existed | A customer could not request the missing report. | Offer a request specifically for whichever report is missing. Both present: show both report links. |
| Fabricated fallback phone | Requests/acceptance notices could be directed to a made-up phone number. | Validate and normalize the supplied number; support Indian 10-digit numbers. With no valid contact, show instructions rather than inventing a destination. |
| Static browser-local acceptance presented as e-signature/team workflow | No identity verification, remote notification or backend record; name and consent optional; storage errors ignored. | Explicitly label local typed acknowledgement, require name and consent, verify persistence before showing success, reject changed/expired/archived proposals, and require the customer to send WhatsApp to notify the team. Remove automatic price-lock/team-follow-up claims. |
| Acceptance visible for missing/failed proposal | Customer saw an action without a loaded proposal. | Hide acceptance and disable PDF until render succeeds. Handle malformed query strings safely. |
| Invented bill and fixed-charge floor | No bill supplied still produced assumed ₹4,500/₹950 figures; a low bill could increase to a ₹650 floor. | Show comparison only for an entered positive bill. Offset comes from the finance engine and is bounded by the entered bill. Calculate the bar width from the actual ratio. Label this as an energy-value illustration excluding fixed charges, duties and export settlement—not a promised payable bill. |
| Guaranteed-sounding depreciation claim / hard-coded tax caption | Assumed 40% depreciation and 25% rate could read as universally applicable; zero tax rate was replaced with 25%. | Editable, bounded depreciation/tax assumptions, zero respected, caption reflects actual rates. Clearly conditional on adviser confirmation of eligibility, asset basis, commissioning date and tax regime. Never net the illustration off investment, payback or projected savings. This audit is not a tax-law certification. |
| Presets cleared equipment select values | Preset labels not in the catalog became empty strings. | Add safe option elements for historical/custom equipment values; use the same form application path for presets and saved proposals. Test all four presets across reload. |
| Presets retained unrelated design/finance data | Old report links, subsidy override, BOM and loans could appear attached to a different system. | Ask for confirmation, preserve customer/saved options, clear those stale values and unspecified module dimensions. Label presets as indicative and require equipment/pricing verification. |
| Savings-page footnote overlapped footer | Body scroll-height checks alone missed actual footer overlap. | Reduce two chart heights modestly; verify content bounding boxes against footer, without changing calculations or cover. |
| Legacy browser harness could exit successfully on failed checks | Failed assertions only logged; it interacted with fields hidden by Essentials mode. | Count failures in exit status, support configured/bundled Chromium, switch to All settings before advanced interactions. |

## Remaining product limitations (explicit, not silently claimed complete)

1. `share.html?p=<id>` reads localStorage in the current browser/origin. It does **not** transfer a proposal to a customer's other device. A clean-browser test confirms the viewer explains this and disables unavailable actions. Use a PDF or proposal file/import until authenticated shared storage is implemented.
2. Typed acknowledgement is **not** a verified digital signature, tamper-proof audit trail, identity check, or automatic notification service. A production e-sign flow needs backend persistence, authentication/verification and delivery confirmation.
3. Arka/PVsyst actions open provided links or prepare a WhatsApp request. They do **not** run simulations or generate reports.
4. Bill and tax figures remain conditional illustrations with stated assumptions; they are not guaranteed utility bills or tax entitlements.

## Release recommendation

Suitable for a **preview review** of the integrated builder and local share workflow with the limitations above. Do not advertise cross-device customer sharing or legally verified e-sign as complete. Keep the PR open; production merge remains a separate user decision.
